JLG Jefferson City – Master System Reference
 
**JLG Jefferson City**
 
Production MES System – Master Reference
 
*Architecture, Logic, Tags, Schedules, Stations, and Integrations*
 
Source: production gateway backups + PLC ACD save log
 
Snapshot: 2026-04-29 (BKD1, BKD2, FRT1, FRT2 + Factory_Automation_PLC_4_29_2026_944)
 
# Table of Contents
 
# 1. Executive Overview
 
This document is the master reference for the JLG Jefferson City Production MES system. It describes how the PLC, the Ignition gateways (front-end and back-end), the Sepasoft MES modules, the Red Viking Navithor AMR fleet, and the supporting databases are wired together so that someone troubleshooting an issue at any layer can identify which component owns the behavior, which gateway the relevant code lives on, and which downstream systems are involved.
 
The system is a dual-redundant Ignition install pinned to version 8.1.49 (build 2025081208). Front-end gateways serve the operator HMIs and run the visible Perspective and Vision projects. Back-end gateways own the OPC connections to the PLCs, the Sepasoft MES module instances, the AMR fleet logic, the run-schedule engine, and all of the heavy-weight scheduled and tag-change logic. Front-ends are interchangeable behind a load balancer; back-ends are specialized — Back-End-1 owns the fabrication and paint side, Back-End-2 owns the assembly side and the Navithor AMR fleet.
 
## 1.1 Plant at a glance

| --- | --- |

| Project family | JLG-NxtGen-MES (frontend-projects, backend-projects on github.oshkoshglobal.com) |
| Ignition version | 8.1.49 (build 2025081208) |

Sections 2 and 3 describe the physical/logical architecture and how the four gateways divide responsibility. # 2. Physical & Logical Architecture
 
## 2.1 Gateway inventory
 
Four Ignition gateways run the Jefferson City production environment. Hostnames follow the corporate convention <site>-<env>-<role>-<platform>-<inventory-tag>. Backups in this snapshot:
 
| **Role** | **Hostname** | **Snapshot file** | **Primary tag provider** |
| --- | --- | --- | --- |
| Front-End 1 | JEF-PRD-FRT1-SP-NAACCIFJCPW01 | ...-FJCPW01_Ignition-backup-20260429-0927.gwbk | (remote: TAGIO1, TAGIO2 via gantagprovider) |
| Front-End 2 | JEF-PRD-FRT2-SP-NAACCIFJCPW02 | ...-FJCPW02_Ignition-backup-20260429-0931.gwbk | (remote: TAGIO1, TAGIO2 via gantagprovider) |

## 2.2 Role split: who owns what
 
Gateway role is decided at runtime by reading the ConfigType for the local SystemName from the environmentGatewayConfig dataset tag (one row per gateway). All major scripts begin with a GatewayConfig.getGatewayType() check and exit early if the script is running on the wrong gateway. This is how identical project code is deployed to all four gateways while only the right one actually executes the side-effects.
 
| **Concern** | **Front-End 1/2** | **Back-End 1 (TAGIO1)** | **Back-End 2 (TAGIO2)** |
| --- | --- | --- | --- |
| Operator HMIs (Perspective/Vision) | Yes | No | No |
| OPC UA to plant PLCs | No | Yes | Yes |
| Sepasoft MES modules running | No | Yes | Yes |
| Areas owned | — | Frame Fab, Boom Fab, Paint | Main Line, Boom/Cab/Engine/Outrigger Subs, Legacy Line |
| Run Schedule generation | No | Yes (PaintLoad, Schedule) | No (consumes BE1 schedule) |
| Navithor AMR fleet logic | No | No | Yes (ALL) |
| Ignition→Navithor commands | No | No (sends via msg handler) | Yes (system.rvNavithor.*) |
| MQTT engine subscription | No | No | Yes (uagv/v2/jlg/AMR_<id>/...) |
| JaMES API calls | No | Yes | Yes |
| AD/LDAP user-source primary | Mirror | Mirror | Mirror (OSKGLOBAL ADHYBRID) |
| Daily/weekly cron jobs | No | Yes | Yes |
 
## 2.3 Network and data flow
 
The high-level data flow is: PLC → Back-End OPC connection → TAGIOx tag provider → (gantagprovider remote) → Front-End → operator browser. Writes from the operator follow the reverse path. AMR telemetry comes in over MQTT and Navithor's HTTP API to BE2; AMR commands sent from any gateway are routed through Ignition message handlers to BE2 because system.rvNavithor.* commands are gateway-scoped to the gateway that holds the Navithor module connection.
 
Database access is direct from any gateway — every gateway has the SCADA datasource configured against db-prd-jefignition1-primary. Heavy queries that drive the run schedule and AMR mission generation execute on the back-ends; the front-ends mostly run lighter operator-driven named queries.
 
# 3. Gateways – Detailed Reference
 
## 3.1 GatewayConfig: the single source of truth
 
All routing decisions go through the GatewayConfig script library (project: FactoryGatewayEvents on back-ends, FactoryControl on front-ends). It reads two tags to discover its own identity:
 
[System]Gateway/SystemName
 
[TAGIO1]JLG/Jefferson City/Admin/environmentGatewayConfig    (or [TAGIO2] if BE1 unreachable)
 
The environmentGatewayConfig tag is a Dataset with columns Environment, ConfigName, ConfigType. GatewayConfig walks that dataset to answer questions like 'who is Back-End-1?', 'who is the JaMES API server?', 'what is the Navithor HTTP URL and API key?'. Most heavy scripts gate on GatewayConfig.getGatewayType() returning 'Back-End-1' or 'Back-End-2'.
 
### Key GatewayConfig functions
 
| **Function** | **Returns** | **Used to gate** |
| --- | --- | --- |
| getEnvData() | (Environment, configDataset) | Bootstrap for all other lookups |
| getGatewayType() | 'Back-End-1' / 'Back-End-2' / 'Front-End-1' / 'Front-End-2' / 'Orchestration' | Most timer + scheduled scripts |
| getBackEnds() | list of BE gateway names | Cross-gateway message broadcasting |
| getBackEnd_1() / _2() | single gateway name | Targeted message sending |
| getFrontEnd_1() | single FE gateway name | Bridging FE→BE actions |
| getOrch() | Orchestration gateway name | Multi-site sync (if used) |
| getUserSource() | Auth profile name (e.g. OSKGLOBAL) | system.user.* calls in admin scripts |
| getSCADAMES() | JaMES SCADA gateway name | MES Management cross-talk |
| getJaMESAPIServer() | JaMES API host | REST calls into JaMES |
| getLoadBalancer() | LB name/address | Logging / link generation |
| getNavithorCustomAPIAddress() | custom API host | AMR commands via REST |
| getNavithorHTTPAddress() | {url, ApiKey} dict | Direct Navithor HTTP calls |
| getDefaultTagProvider() | '[TAGIO1]' or '[TAGIO2]' | Tag path resolution on BE1 vs BE2 |
| getGatewayAreas() | list of plant areas owned | Filtering schedule + station scripts |

# 4. PLC Layer
 
## 4.1 Source file in this snapshot
 
FactoryAutomationPLCBackups/Factory_Automation_PLC_4_29_2026_944 is a Studio 5000 ACD (compiled binary) save file, not an L5X export. The first ~600 lines of the file are a human-readable change-log header showing every save event with timestamp and firmware revision; the remainder is the proprietary binary controller image, which can only be opened in Studio 5000.
 
Implication for troubleshooting from this document: the routine, AOI, UDT, and tag definitions in the PLC are NOT directly inspectable from this snapshot. The controller's role and behavior are inferred from the OPC tag paths the back-end gateways subscribe to, and from how the Ignition scripts read and write those tags.
 
## 4.2 Controller metadata (from the ACD save log)
 
| **Property** | **Value** |
| --- | --- |
| File creation | 2024-09-27 15:28:59 EDT |
| Studio 5000 version | V35.00.00 / firmware 3865.000 (V35+ supports DT data type) |
| Most recent save (in this file) | Multiple saves logged; final save is the snapshot point |
| Naming | Factory_Automation_PLC_<date>_<sequence#> — sequence resets daily |
| Backup mechanism | Manual or scheduled .ACD copy from the engineering workstation |
 
## 4.3 What the PLC controls (inferred from Ignition)
 
By tracing the tag paths read and written by the gateway scripts, the Factory Automation controller owns the following plant-floor functions:
 
- Station-level cycle control on every assembly station (TF / TB / TC / TE / TX / LL prefixes — Main Line and the Subs).
 
- Station-level cycle control on every fabrication and paint station (TW Frame Fab, TT Boom Fab, PT Paint).
 
- Material movement signals — "nextComponentLoaded" handshakes used by the run-schedule logic to advance station queues.
 
- AMRControl handshake tags per station (AMRNumberAssignedToStation, SymbolicPointToPLC, destinationSymbolicPoint, nextStationToLoad).
 
- Paint cell coordination at PT010A and PT010B (the nextComponentLoaded tag-change handlers in BE1 react to these specifically).
 
- Status feedback for the Station-Sentinel STATION_STATUS_LABELS enum: 0 No Build, 1 Waiting for Cycle Start, 2 Work in Progress, 3 Work Complete, 4 Process Aborted, 5 Interlock Bypassed, 6 Alarm Active, 7 Help Requested, 8 Buffer Station, 9 Material Exit Confirmation, 10 Manual Block.
 
## 4.4 To get a documentable PLC export
 
Open Factory_Automation_PLC_4_29_2026_944 in Studio 5000 V35+ on the engineering workstation, then File → Save As → set type to L5X. For documentation use, exporting per-program / per-AOI / per-UDT yields smaller diffable files than a single whole-controller L5X. Export targets that should be captured for completeness:
 
- All UDTs (Logical Organizer → User-Defined → right-click → Export Data Type)
 
- All AOIs (Add-On Instructions → right-click → Export Add-On Instruction)
 
- Each Program (Tasks → MainTask → right-click → Export Program)
 
- Controller Tags and the Module Configuration

## 6.5 Station-Sentinel (FE1 only)
 
Quoting the project description from the snapshot: "Station-Sentinel gives visibility into what's happening at each station and where things get stuck. It allows supervisors to see the current state, understand why movement isn't happening, and safely override or recover the process when needed."
 
All logic lives in the StationSentinel/StationTruth script package (1,464 lines). Exposes a get_health endpoint, get_stations(area, station_name) for filtered station lists, get_layout(station_name), and a build_station_truth() function that reads the station's PLC state and aggregates it into a single supervisor-facing payload. Uses the WorkStationAssignment table to map StationName → Area → SymbolicPoint, then translates raw PLC status integers via STATION_STATUS_LABELS into the human-readable labels visible in the supervisor view.

# 11. Stations, Areas, and Station Types
 
## 11.1 Naming convention
 
Every station has a 2-letter prefix that uniquely identifies its area, followed by a 3-digit station number. Where applicable, a single trailing letter denotes a sub-cell (A/B). # 12. External Integrations
 
## 12.1 Red Viking Navithor (AMR fleet)
 
Navithor is the AMR fleet manager. The Ignition module exposes system.rvNavithor.* functions which are gateway-scoped — they only run on the gateway that holds the connection (BE2). Three communication channels are in use:
 
- **HTTP API** — Direct REST calls via system.rvNavithor.* (status pulls, mission create/abort, agv commands). Address and API key are read from environmentGatewayConfig via GatewayConfig.getNavithorHTTPAddress() returning {url, ApiKey}.
 
- **MQTT** — AMR HMI and Prosoft data flow over MQTT topics uagv/v2/jlg/AMR_<id>/... (state, order, fromHMI/Prosoft_info_AMR_hours). Subscribed via Ignition's MQTT Engine module on BE2.
 
- **Custom API** — An auxiliary endpoint at GatewayConfig.getNavithorCustomAPIAddress() — used for site-specific commands beyond the stock API.
 
### Mission lifecycle
 
1. Front-end view sends createMission to BE2 with { stationName }. 2. BE2 reads the station's AMRControl UDT to get AMRNumber, station symbolic point, and destination symbolic point. 3. BE2 reads the AMR's Navithor state and InProductionBool — if not in production, calls startProduction(amrNumberInt). 4. If state==15 (hold), calls system.rvNavithor.symbolicPoint.releaseHoldToCustomTarget(...). 5. Otherwise builds a mission_object with a unique ExternalId (epoch ms) and one Drive step targeting the destination symbolic point, then calls system.rvNavithor.mission.create.send(mission_object). 6. Publishes the destination station name to the AMR's HMI over MQTT (uagv/v2/jlg/AMR_<id>/toHMI/destinationStationName).
 
### Mission template variant
 
If the payload includes missionTemplateName, BE2 calls system.rvNavithor.mission.activateMissionTemplate(...) instead. Mission templates are maintained in Navithor system files by JLG and contain pre-defined multi-step missions (queueing, sub-routing) that can't be expressed easily in a single Drive step.

# 14. Operational Reference & Troubleshooting
 
## 14.1 Where do I look first?
 
| **Symptom** | **Where to look first** | **Why** |
| --- | --- | --- |
| A station is stuck — operator says nothing happens when they hit cycle start | Station-Sentinel get_layout(stationName) on FE1; cross-check the station's status integer 0–10 (§11.3). | Station-Sentinel translates raw PLC state into a human-readable label and surfaces the most common stuck reasons. |
| AMR not arriving at a station | BE2 logger 'Create Mission Message-Handler' and 'AMR Abort Command'; tag [TAGIO2]JLG/Jefferson City/Fleet/Navithor Status/isConnected; tag [TAGIO2]JLG/Jefferson City/Fleet/AMR Data/AMR_<id>/fromNavithor/State. | createMission only runs if Navithor is connected; State==15 means held; in-production flag matters. |
| AMR status panel is stale | Populate AgvStatus timer on BE2; AgvStatus_UpdateInProgress tag stuck True is the failure mode. | Belt-and-suspenders lock; manual unset clears it but root-cause is usually a Navithor HTTP timeout in the timer. |
| MES / batch queue page errors | BE1 or BE2 logger 'Gateway/Timer.ProductionModuleStatusMonitor'; tag ProductionStatusMES/ProductionModuleRunning. | isProductionStarted() is unreliable; the timer corroborates it by actually trying getEntries. |
| Run Schedule did not refresh overnight | Cron job at 04:15 on BE1 (regenSecondarySchedules) — check gateway logs for that timestamp. | It's the only thing scheduled to update the master schedule's lastMasterScheduleRefresh timestamp. |
| A user added in AD doesn't appear in Ignition | Admin.UserManagementSync.addUser logs on BE; userManagementSync message handler on BE; LDAP-S health. | The handler is what actually syncs them — adds via system.user / system.roster. |
| Paint Load queue not advancing | Tag-change scripts on PT010A and PT010B nextComponentLoaded; logger 'gatewayScript' on BE1. | The queue is maintained by the rising/falling-edge handler that pushes/pops nextStationToLoad. |
| Cab tester (TMH) station offline | TMHCabTester01/02 tag providers on FE; CabTesterEdits package logs on FE. | Cab tester is its own provider tree; problems often manifest as that provider being disconnected. |
| JaMES lookups returning empty | BE FactoryGatewayEvents jamesInteractions logger; GatewayConfig.getJaMESAPIServer() URL reachable? | The integration is a thin REST shim — failures almost always come from the JaMES side. |
| Front-end can't reach a back-end resource | Gateway network connection statuses on every gateway; TAGIO1/TAGIO2 gantagprovider quality. | All FE→BE calls run over the gateway network; degraded quality breaks bindings + message handlers. |

## 14.3 Redundancy / failover patterns
 
Front-ends are stateless behind the load balancer, so failover is automatic — operators just hit the same URL. Back-end role split is not redundant: if BE1 is down, run-schedule generation, paint logic, and TAGIO1 stop. If BE2 is down, the AMR fleet stops accepting new missions and Sepasoft Batch on TAGIO2 stops. There is no automatic role swap; recovery is to restore the failing gateway. In extreme cases the environmentGatewayConfig dataset can be edited to point a healthy gateway at the missing role, but that is an engineer-supervised maintenance action — most scripts gate strictly on the role string.

## 15.4 Limits of this document
 
This document captures the architecture, the project + script catalog, scheduled / event scripting, tag tree shape, and integration touch points — i.e. everything that's directly readable from the four gateway backups. It does NOT include:
 
- Full PLC routine / UDT / AOI / tag definitions — the ACD save is binary; an L5X export is required (see §4.4).
 
- The full text of every named query (~600+ across all projects) — you'll find them in the project export under com.inductiveautomation.webdev or ignition/named-query/.
 
- The full source of every script-library function (~32k lines) — they're in ignition/script-python/<package>/code.py.
 
- The Perspective view JSON for every view (~800 views total) — they're in com.inductiveautomation.perspective/views/<folder>/view.json.
 
- Tag JSON definitions exported from the providers — those would be a separate Tag Export.
 
If you need a physical reference for any of those, ask Claude with this document loaded plus the specific project export (or the relevant snippet) — that's the supported workflow when the full exports won't fit in the chat context.
